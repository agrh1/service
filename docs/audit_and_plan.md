# Аудит реализации и план доведения до ТЗ

Документ служит дорожной картой: что уже есть в репозитории, что расходится с ТЗ и как безопасно довести систему до требуемого состояния без остановки работающего сервиса.

## Краткое состояние по сервисам
- **Telegram‑бот**: базовая маршрутизация команд, логирование, health‑проба есть, но нет авторизации по БД и ролям; отсутствует поддержка команд ТЗ (сброс пароля, запрос/создание каталогов, администрирование пользователей). См. `telegram_bot/main.py` и `handlers` — команды ограничены стартом, статусом, заглушкой логов/тикетов.【F:telegram_bot/main.py†L1-L49】
- **IntraService‑Service**: FastAPI с health и несколько заглушечных endpoint’ов; нет опроса заявок, парсинга системного лога, работы с категориями и пользователем `seaf_user`. Корреляционный ID и JSON‑логирование частично есть, но бизнес‑логика отсутствует.【F:intraservice_service/api.py†L1-L80】【F:intraservice_service/api.py†L82-L118】
- **Seafile‑Service**: Flask‑приложение содержит дублирование и смешение старого/нового кода, нет работы с несколькими инстансами/репозиториями, генерация ссылок не защищена паролями/TTL, нет удаления просроченных ссылок. Корреляционный ID ведётся фрагментарно.【F:seafile_service/api.py†L1-L88】【F:seafile_service/api.py†L90-L153】
- **Config‑Portal (Django)**: есть заготовка, но отсутствуют модели/страницы для настроек интеграций, пользователей бота, мэппинга категорий → Seafile и панель состояния. Учебник поверхностный.【F:django_portal/tutorial.md†L1-L16】
- **Инфраструктура**: docker‑compose запускает множество контейнеров и экспортеров, но `.env.example` неполный (нет секретов Seafile/IntraService/Django), прод‑процесс обновления не описан для zero‑downtime, CI/CD отсутствует в репозитории GitHub Actions/GitLab CI (есть только общие слова в `docs/operations.md`).【F:docker-compose.dev.yml†L1-L196】【F:.env.example†L1-L22】【F:docs/operations.md†L1-L33】

## Ключевые расхождения с ТЗ
1. **Отсутствие основной функциональности**: нет опроса заявок со статусом `StatusID=31`, нет парсинга eventlog, нет фильтров логов и уведомлений в Telegram, нет автоматического управления категориями/`seaf_user`.
2. **Seafile**: не поддержаны многократные инстансы и репозитории, нет привязки к категориям, отсутствует генерация download‑ссылок с паролем и сроком 7 дней, нет удаления истёкших ссылок.
3. **Telegram‑бот**: нет регистрации пользователей/ролей, нет команд сброса пароля, добавления пользователя, запроса каталогов с вызовом Seafile‑Service, нет rate limiting для опасных операций.
4. **Config‑Portal**: нет UI/моделей для управления настройками, пользователями бота, мэппингами категорий, фильтрами логов и справочником Seafile‑инстансов.
5. **Логирование/мониторинг**: сервисы частично отдают `/health`, но нет унифицированных метрик `/metrics` у всех сервисов, нет корреляционного ID в цепочке запросов, нет алертов/дашбордов.
6. **Безопасность/конфигурация**: переменные окружения неполные, секреты не маскируются, отсутствуют ограничения частоты и контроль токенов сервисов, нет рекомендаций по TLS/Nginx.

## План доработок без простоя
Работать поэтапно: каждое обновление выкатывать через новую версию контейнера с health‑чеками и обратимым откатом. Ниже указаны шаги, что делать и какие файлы заменить.

### Этап 1. Технический долг и безопасные каркасы
1. **Привести API IntraService‑Service к чистому состоянию**: заменить `intraservice_service/api.py` на подготовленный каркас из `docs/blueprints/intraservice_api.py` (поддержка health/metrics, корреляция, заглушки опроса заявок и eventlog). Раскатка: собрать новый образ, поднять параллельный контейнер `intraservice_v2`, переключить трафик в `api_gateway`, удалить старый после проверки.
2. **Очистить Seafile‑Service**: заменить `seafile_service/api.py` на вариант из `docs/blueprints/seafile_api.py` — единый Flask‑app, корректные схемы запросов/ответов, задел для нескольких инстансов и TTL download‑ссылок. Раскатка аналогична: собрать новый образ, выполнить `docker compose up -d seafile` с тегом `-v2`, проверить `/health` и `/metrics`.
3. **Расширить `.env.example`**: добавить переменные Seafile/IntraService/Django/Telegram/Redis/Prometheus, маскировать секреты. Это не требует простоя — файл примерный; рабочий `.env` остаётся без коммита.
4. **Подготовить CI**: добавить GitHub Actions workflow для lint/pytest и сборки образов; деплой на прод — ручной триггер. Запуск CI не затрагивает прод.

### Этап 2. Функциональные интеграции
1. **IntraService опрос**: реализовать в `IntraServiceClient` (каркас в blueprint) методы `fetch_open_tickets`, `fetch_eventlog_page`, хранить смещения в Redis/Postgres. Добавить Celery beat задачи (interval из БД). Отправлять события в очередь для Telegram‑бота.
2. **Seafile**: реализовать `SeafileRouter` с таблицей инстансов/репозиториев; генерация upload/download с паролями (12+ символов) и TTL 7 дней; фоновые задачи удаления просроченных ссылок. Сохранение связей в Postgres.
3. **Telegram‑бот**: расширить репозиторий пользователей, добавить middleware авторизации, команды `reset_password`, `register_user`, `get_logs_dir` с вызовами API. Включить rate limiting флагами.
4. **Config‑Portal**: создать модели Django для настроек (IntraService, Seafile, Telegram, интервалы), мэппинга категорий, фильтров логов и пользователей бота; сделать admin и простые API/ViewSet для портала.

### Этап 3. Наблюдаемость и безопасность
1. Привести все сервисы к `/metrics` (Prometheus) и `X-Correlation-ID` в логах. Добавить алерты в Prometheus по доступности интеграций и росту ошибок.
2. Обновить Nginx конфигурацию: TLS‑терминация, маршрутизация на portal/api_gateway/metrics (только с внутренней сети), basic auth на /metrics.
3. Включить лимиты частоты на команды бота и защищённые операции Seafile, логировать аудит в Postgres.

### Этап 4. Учебник и эксплуатация
1. Расширить `django_portal/tutorial.md` разделами по IntraService/Seafile интеграции, бэкапам, обновлениям без простоя, примерам добавления новых категорий.
2. Добавить разделы в `docs/operations.md` о пошаговых откатах, тестовом прогоне миграций и smoke‑тестах `/health`/`/metrics` после выката.

## Каркасы файлов (готовые замены)
Файлы ниже можно положить поверх существующих (или скопировать в ветку feature и включить в сборку). Все ключевые места помечены комментариями на русском.
- `docs/blueprints/intraservice_api.py` — новая версия `intraservice_service/api.py` с FastAPI, корреляцией, метриками и интерфейсами для опроса заявок и eventlog.
- `docs/blueprints/seafile_api.py` — новая версия `seafile_service/api.py` с единым приложением, схемами запросов и заделом под несколько инстансов.

## Порядок раскатки изменений на работающий сервис
1. **Подготовка**: обновите `.env` (без коммита), соберите образы `docker compose -f docker-compose.prod.yml build intraservice seafile` с новыми файлами.
2. **Бэкап**: выполните скрипт `scripts/backup_postgres.sh` или `docker compose -f docker-compose.prod.yml run --rm backup`.
3. **Поочерёдное обновление**:
   - Запустите новый контейнер с суффиксом `-v2` (через временное переопределение `container_name`/`image` или профиль docker compose).
   - Проверьте `/health` и `/metrics` новых экземпляров.
   - Переключите зависимости `api_gateway` на новые сервисы (env `INTRASERVICE_URL`, `SEAFILE_SERVICE_URL`), выполните `docker compose up -d api_gateway`.
   - После стабилизации удалите старые контейнеры `intraservice_service`/`seafile_service`.
4. **Smoke‑тесты**: убедитесь, что Prometheus видит метрики, Telegram‑бот отвечает на базовые команды, портальные страницы открываются.
5. **Откат**: при проблемах верните переменные `INTRASERVICE_URL`/`SEAFILE_SERVICE_URL` на старые сервисы и выполните `docker compose up -d api_gateway`; замените образы на предыдущие теги и перезапустите сервисы.

## Теория: почему так
- **Пошаговые выкаты** через два экземпляра сервиса позволяют обновлять без простоя и держать возврат на предыдущую версию.
- **Корреляционный ID** облегчает трассировку через Telegram → IntraService → Seafile; единый JSON‑формат логов нужен для будущего ELK/Loki.
- **Чёткие схемы запросов** (Pydantic) предотвращают падения из‑за невалидных данных и дают понятные ошибки пользователю бота и порталу.
- **TTL и пароли для download‑ссылок** — требование безопасности из ТЗ; фоновые задачи обеспечивают автоматическую уборку, чтобы не копился мусор.
- **Разделение настроек через БД и портал** даёт централизованное управление без пересборки контейнеров.
